# Backend architecture and team conventions

This is a feature-module NestJS application. `src/modules/` is our team convention,
not a mandatory NestJS folder name. Module ownership and explicit dependency
injection matter more than directory depth.

## Layout

```text
api/
  prisma/                 # Schema and committed SQL migrations
  scripts/                # Operator scripts (including promote-admin.mjs)
  src/
    common/
      decorators/         # Reusable input helpers
      rate-limit/         # Shared database-backed quota module
    config/               # Startup environment validation
    generated/prisma/     # Generated by Prisma; never edit or commit
    modules/
      access/             # Account status policy and moderation event bus
      admin/
        dto/              # Admin request validation
        guards/           # Admin-only authorization
        admin.controller.ts
        admin.service.ts
        admin.module.ts
      auth/
        decorators/
        dto/
        guards/
        auth.controller.ts
        auth.service.ts
        auth.module.ts
      health/             # Existing liveness endpoint
      realtime/           # Socket authentication, matching, chat and signaling
    prisma/               # PrismaModule / PrismaService
    app.module.ts         # Composition root
    app.setup.ts          # Shared HTTP security, CORS, validation and prefix
    main.ts               # Bootstrap and process lifecycle
  test/                   # Unit wiring checks and real-PostgreSQL integration tests
```

## Ownership and dependency rules

- Keep feature DTOs, guards and types inside their feature. Move a helper to
  `common/` only when it is reusable across features; do not add empty folders.
- A controller handles HTTP concerns and delegates business decisions to a service.
  A gateway handles Socket.IO concerns. The current realtime gateway still owns
  matchmaking/signaling state; extracting those services is a separate behavioral
  refactor, not part of this directory migration.
- Import the module that exports a service. Do not register that service again in
  another module's `providers`: that can create multiple instances/event buses.
- PrismaModule, AccountAccessModule and RateLimitModule are explicitly imported;
  none are global. ConfigModule is global by deliberate application convention.
- Auth imports Prisma, Access and RateLimit. Admin imports Prisma, Access and Auth.
  Realtime imports Prisma, Access, RateLimit and its JWT module. Access and
  RateLimit each import Prisma. Health has no database dependency.
- Cross-feature consumers use exported providers, never another controller.
  Common utilities must not import business feature modules. Avoid circular
  dependencies; do not hide them with `forwardRef` without a design review.
- DTOs validate incoming data; services enforce business rules and authorization
  invariants. A DTO file alone does not enable validation.
- Use relative imports consistently. TypeScript path aliases alone do not teach
  production Node/Jest how to resolve them, so this refactor adds no aliases.
- Tests import the new paths directly; no compatibility barrels hide old paths.

## Add a feature

From `api/`, use the locally installed CLI:

```bash
npx nest generate module modules/debate-setup
npx nest generate controller modules/debate-setup
npx nest generate service modules/debate-setup
```

Inspect the generated module registration in AppModule, keep DTOs under the
feature's `dto/`, and import only the provider modules the feature needs.
Do not duplicate a module if it was already created locally. CLI-generated spec
files should contain meaningful tests or be replaced with focused tests in `test/`;
current test scripts discover `test/*.unit-spec.ts` and `test/*.e2e-spec.ts`.

## Verify a change

```bash
cd api
npm ci
npm run build
npm run typecheck
npm run test:unit
```

For integration tests, point DATABASE_URL at a **dedicated disposable test database**,
apply migrations there, then run `npm run test:e2e`. The suite deletes test data and
must never run against a production or personal database. CI supplies PostgreSQL 16.

`module-wiring.unit-spec.ts` compiles each feature without AppModule to catch hidden
DI dependencies and verifies a single account-access event bus is shared. Existing
integration tests verify auth, rate limits, realtime and moderation behavior.

## Migration notes

Old `src/auth`, `src/admin`, `src/access`, `src/realtime` moved into `src/modules/`.
HealthController moved into HealthModule. The trim decorator moved under
`common/decorators/`; quota files moved under `common/rate-limit/`; admin DTOs and
guard moved into feature subfolders. Update local uncommitted imports accordingly.
No route, socket event, environment variable, database schema or npm dependency
changed. `scripts/promote-admin.mjs` stays in the same location. Build deletes stale
dist output through the existing Nest CLI configuration.

## Production boundary

This provides a maintainable code organization, not a certification of deployment
readiness. Realtime matching and moderation notifications remain in-process, so run
one realtime API instance until distributed state/pubsub is implemented. Configure
and test TURN, HTTPS/cookie domains, database backups, monitoring and trusted proxy
handling for your deployment. Health is liveness only, not database readiness.
Do not add Swagger, a repository abstraction, CQRS or microservices solely to make
the folder tree larger. Introduce infrastructure when a concrete requirement needs it.
